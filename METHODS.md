### Interpretation notes (assumptions made explicit, since no follow-up round was triggered)
- **"A user should be able to change prize specific questions in the middle of the game"** (instructions.md, Users section) is interpreted as *a user may change their own submitted answers* to a prize's questions any time before that prize's announcement — not that users edit the question definitions themselves. Question definitions/content are admin/config-only.
- **Numeric "guesstimate" questions** (average age, total American citizens, etc.) are NOT free-text numeric entry. Per instructions.md ("no more than four, maybe five alternative answers" applies to *every* question), these are presented as a small set of bucketed choices (e.g., ranges), each carrying its own historical-frequency-derived odds, scored with the exact same `points = 1 / probability` mechanism as every other question. This keeps one scoring engine for the whole game instead of a second, distance-based system.
- **Odds/probabilities are static**, computed once from the 2006–2025 historical table in `nobeldata.md` and hardcoded into each question's answer options at content-authoring time. They are not recalculated dynamically from how this year's players answer (no pari-mutuel pool betting) — this matches the worked example in instructions.md ("1 laureate 4/20 times... 5 points = 1/(4/20)").
- **Literature genre and other judgement-based gradings** (e.g., "prose, poetry or other", motivation-phrase matches) cannot always be graded by pure string matching. The admin override page doubles as a **grading confirmation step**: the scraper proposes an answer/grading, an admin confirms or corrects it before points are posted. This reuses the same page built for scraping failures instead of a second UI.
- **2026 Nobel week dates** — confirmed with the user 2026-09-28 (a conflicting instruction had briefly suggested swapping Physics and Medicine; the user confirmed the reading below, which matches `nobeldata.md`'s own caveats and the traditional announcement order): Medicine Mon 5 Oct, Physics Tue 6 Oct, Chemistry Wed 7 Oct, Literature Thu 8 Oct, Peace Fri 9 Oct, Economics Mon 12 Oct (week 42, not week 41 — instructions.md's "week 41" framing is now one week off for 2026 and is treated as informational, not a hard constraint).

## Architecture

**Stack:** Next.js 14 (App Router, TypeScript), single Node deployment, PostgreSQL, Prisma ORM, Tailwind CSS + shadcn/ui (Radix-based, accessible by default), Resend for email, deployed as one Railway service.

**Why a single Next.js app instead of separate frontend/backend:**
- The whole product is one page (login → single quiz/leaderboard/prize-info page) plus a small admin surface. A split frontend/backend adds deployment surface (two services, two URLs, CORS) for no real benefit at this scale.
- Railway bills per service; one service keeps this on the free/hobby tier as requested.
- Next.js Server Components let the single page read from Postgres directly for logged-in state, the quiz form, and the leaderboard without hand-rolling a separate REST/GraphQL layer — Route Handlers (`app/api/*`) cover the few places that need imperative POST/GET semantics (submit answer, admin override, cron tick).

**Why Prisma over a raw SQL layer or Drizzle:**
- Small schema, small team (one dev). Prisma's migration workflow (`prisma migrate deploy` in the Railway build step) and generated types reduce hand-written boilerplate for what is a fairly conventional relational schema (users, questions, answer options, submissions, results).

**Why a custom auth implementation instead of NextAuth/Auth.js:**
- Requirement is specifically "regular" security: email + password + a verification email via an existing Resend account. NextAuth's credentials provider does not include first-class email verification or password reset flows; wiring those on top of it isn't meaningfully less code than a small, fully-understood custom implementation.
- Design: `bcrypt` password hashes; a `sessions` table (DB-backed, not JWT) referenced by a signed, `httpOnly`, `Secure` cookie, so sessions can be revoked server-side; a `verification_tokens` table for both email verification and password reset, single-use, time-limited; Resend sends both emails. Login is blocked until `emailVerified = true`.

**Why an in-process scheduler instead of Railway Cron or a second worker service:**
- Railway keeps a web service's process alive (unlike serverless platforms), so a simple `setInterval`-based checker registered once via Next.js `instrumentation.ts` can poll on its own schedule without needing a second billed service or Railway's Cron Jobs add-on (which sits on paid plans). This satisfies "start 5 minutes after the announcement time, then retry regularly" from instructions.md at zero extra infrastructure cost.
- Each prize category has its own small scraper config (candidate URL patterns + parsing rules), since instructions.md notes the announcement page URLs vary year to year. If a scrape fails after a bounded number of retries (or produces a result an admin hasn't confirmed), it surfaces on the admin override page instead of silently blocking the game.

**Why bucketed multiple-choice for every question type (including numeric ones):**
- Keeps exactly one scoring formula (`points = 1 / probability`) across the entire app — no branching logic between "categorical" and "numeric" question types in the scoring engine, admin tooling, or UI components. Simpler code, and it's what instructions.md's own worked example describes.

**Timezone handling:** all `announcementAt` / `answerDeadline` timestamps are stored in UTC (derived from Stockholm/CET-CEST source times at content-authoring time) and rendered client-side via `Intl.DateTimeFormat` in the visitor's local timezone, with the countdown timer computed client-side against the UTC deadline.

**Accessibility & design:** warm/floral palette (marigold, coral, sage, lavender) checked against WCAG AA contrast; shadcn/ui (Radix primitives) for interactive components (accordions, tabs, dialogs) to get keyboard nav and ARIA semantics for free; a playful display font for headings paired with a highly legible body font; no information conveyed by color alone (icons/text accompany every status indicator).

**GDPR:** a short, plain-language notice at signup explaining that the email address is stored solely for login and result notification, is never shown to other users, and can be deleted on request. Confirmed 2026-09-28: deletion removes the account **and** its historical answers/submissions/scores outright — no anonymized retention of past answers.

## Scope boundary (one-off 2026 build)

Per answer #2, the schema is not artificially generalized for multi-year reuse. It is deliberately simple: one `season` concept exists (a single row) rather than a `years` table with foreign keys everywhere. If the game is run again next year, question content and historical odds get updated in place; this is called out explicitly rather than silently over-engineered "for the future."

## 2026-09-28 — Implementation notes (Phase 0/1 scaffolding)

`create-next-app` and `prisma init` both generate an `AGENTS.md`/skills bundle warning that their installed versions have moved past this model's training data. That turned out to be true in ways that changed the plan below — recorded here so later work doesn't rediscover the same surprises.

- **Versions pinned:** Next.js `16.3.6`, React `19.2.8`, Prisma CLI + `@prisma/client` both pinned to the exact same stable version, `7.10.0` (not `^7.10.0`) — `npm install prisma @prisma/client` on its own resolved to a `prisma@8.0.0-rc.17` / `@prisma/client@7.10.0` mismatch, which is a prerelease CLI paired with a stable client. Exact-pinning both to the latest matching stable release avoids that drift; re-check both together before ever bumping one.
- **Prisma 7 requires a driver adapter** for every SQL provider — there is no more implicit `node_modules`-generated client with a bundled engine binary. Added `@prisma/adapter-pg` + `pg`, and `src/lib/prisma.ts` constructs `new PrismaClient({ adapter: new PrismaPg({ connectionString: ... }) })` rather than the old bare `new PrismaClient()`.
- **Generated client location moved out of `node_modules`.** The schema's `generator client` block now requires an explicit `output` path; ours is `src/generated/prisma`, imported as `@/generated/prisma/client`. That directory is gitignored and regenerated via `npx prisma generate` (already wired into `postinstall` is *not* set up — remember to run it after every fresh clone/`npm install`, and Railway's build step must run it before `next build`).
- **Config moved out of `schema.prisma`.** The datasource block only declares `provider = "postgresql"`; the actual `DATABASE_URL` (and future `directUrl`/`shadowDatabaseUrl` if Railway's pooler needs them) lives in `prisma7.config.ts` at the repo root, loaded via `import "dotenv/config"`. The Prisma CLI auto-detects `prisma7.config.ts` — no need to rename it to `prisma.config.ts`.
- **Project is ESM-first** (`"type": "module"` in `package.json`), because the generated Prisma client uses `import.meta.url` internally and Prisma's own v7 upgrade guidance recommends ESM-first over forcing `moduleFormat = "cjs"`. All hand-written config files were already `.ts`/`.mjs`, so this had no fallout — confirmed via a clean `npm run build` and `npm test` after the switch.
- **Standalone scripts (seed scripts, one-off checks) do not get `.env` for free.** Next.js loads `.env` automatically for `next dev`/`next build`/`next start`, but running a script directly via `tsx` does not — use `node --env-file=.env node_modules/.bin/tsx <script>` (or add `import "dotenv/config"` at the top of the script) or `DATABASE_URL` will silently fall through to `pg`'s OS-user-based default connection instead of erroring clearly.
- **Turbopack root:** explicitly set `turbopack.root` in `next.config.ts` to the project directory. Without it, Next.js searched upward for a lockfile and found an unrelated one directly in the home directory, which would have silently mis-scoped file tracing.
- **`npm audit` reports 4 high-severity findings** (`deepmerge-ts`, `mysql2`) that are transitive dependencies of the Prisma CLI's multi-database tooling, not of `@prisma/client` or anything shipped at runtime. `npm audit fix --force` would downgrade to `prisma@6.19.3`, an older major we don't want. Accepted as a build-tool-only risk for now; revisit when Prisma ships a patched CLI release.
- **Local dev database:** a Homebrew-managed local Postgres 14 (already running on this machine) hosts a scratch `nobel_quiz_dev` database for migration/seed development before Railway credentials are available. `prisma migrate dev` and a manual `$queryRaw`/`user.count()` round trip both verified against it.
- **Test runner:** Vitest (not Jest) — lighter config for a Next.js + ESM project. `npm test` runs `vitest run`. First test suite covers the Phase 1.2 points calculator (`src/lib/scoring.ts`), matching instructions.md's worked example (4/20 → 5 points) plus zero/overflow guards.

## 2026-09-28 — Question content (Phase 2) and the citizenship-data caveat

`prisma/seed.ts` now holds all 16 questions (12 prize-specific + 4 whole-week) and their odds, sourced from `nobeldata.md`. Most odds are direct quotes of numbers already computed in that document (laureate-count splits, Literature's genre split, the female-laureate-count buckets). Three questions had no ready-made historical frequency in the document and were **computed from its raw per-laureate tables instead of estimated**, each cross-checked programmatically rather than by hand:

- **Peace individual/organisation/mixed split (11/6/3):** tallied from Tab 6's year-by-year laureate list.
- **"Average laureate age > 72" (2/20 — only 2015 and 2017):** computed by encoding every laureate's age across all six prizes, 2006-2025, into a script and averaging per year. Organisations (no age) were excluded; the one dual-value age ("73/74" for Kosterlitz, 2016) was averaged to 73.5.
- **"American citizens across all six prizes" bucketed 11/7/2 for ≤6 / 7-8 / 9+:** computed the same way, counting any citizenship field containing "US" once per laureate (including dual citizens, per nobeldata.md's own convention), organisations contributing zero. The resulting per-prize 20-year totals (Physics 26, Chemistry 31, Medicine 30, Economics 37, Literature 2, Peace 3) were cross-checked against nobeldata.md's own approximate cumulative totals ("~40/~34/~31/~22–26/3/2") — exact matches for Literature, Peace, and Chemistry; within a few for the others, which is expected given the document's own caveat that **citizenship is its least reliable column** (science-prize citizenship isn't published by nobelprize.org and comes from secondary biographical sources).

Because of that caveat, the "American citizens" whole-week question's odds carry more uncertainty than the others despite being computed rather than guessed. Flagged here rather than silently presented as equally solid; worth a lighter-touch sanity check (not a full re-derivation) before the game goes live, and a natural candidate to revisit if real 2026 citizenship data surfaces something the historical count missed.

Placeholder announcement **times** (not dates, which are confirmed) were assigned per prize based on each prize's typical historical announcement hour, converted from CEST/CET to UTC — nobelprize.org does not publish exact times this far in advance. These are clearly commented as placeholders in `prisma/seed.ts` and should be reconfirmed (or ideally scraped automatically) closer to the date, per Phase 6.

## 2026-09-28 — Auth (Phase 3) decisions

- **Session tokens are a separate high-entropy field, not the row's cuid.** `Session.token` (via `crypto.randomBytes(32).toString("base64url")`) is what's stored in the cookie and looked up; the cuid `id` stays an internal primary key. Cuids are collision-resistant but not designed as unguessable security tokens, so reusing one as a session credential would have been a subtle weakening — caught before any code depended on it, required a one-time local migration reset (scratch DB, no real data lost).
- **Rate limiting is in-memory, per-process, per-IP** (`src/lib/rateLimit.ts`), not Redis-backed. Matches the "small, private, single Railway instance" answer from the clarifying-questions round — state resetting on restart or not being shared across instances is an accepted tradeoff at this scale, not an oversight. Revisit if the game ever runs on more than one instance.
- **Email verification is enforced at login, not at signup.** An account can be created without a verified email, but `login` explicitly checks `emailVerified` and returns a specific message rather than a generic failure — this was a deliberate call to keep the signup step itself simple (no need to hold the request open across the Resend call) while still gating actual game participation on verification.
- **Password reset revokes all of that user's sessions**, not just prompts a re-login. A reset implies the old password (and anything a session was established under) shouldn't remain trusted.
- **Verified with a real headless browser (Playwright), not just server-side logic.** A throwaway Playwright script drove the actual rendered UI — signup, blocked-login-before-verification, verification, login, logout, forgot-password, reset, old-password-rejection — through `localhost:3000` against the local dev DB, reading the dev-fallback email tokens out of the running server's own log output (no debug API route was added, since a token-exposing endpoint would be a real security hole if ever left in). The script itself wasn't committed (it hardcoded a machine-specific log path); Phase 10 should build a proper committed E2E suite instead, ideally with a swappable in-memory email transport rather than log-scraping. Playwright itself **is** kept as a devDependency for that future work.
- **Found and worked around a Next.js App Router quirk while writing that verification script:** Next injects its own accessibility route-announcer element (`<div id="__next-route-announcer__" role="alert">`) into every page for client-side navigations, which collided with a naive `[role="alert"]` selector meant to target this app's own inline form errors. Any future E2E work should scope error-message selectors more specifically (e.g. `p[role="alert"]`, or a dedicated `data-testid`) rather than bare `[role="alert"]`.

TASKS.md still showed all of Phase 4 as `[ ]` despite the UI, submission flow, scoring display, and leaderboard already being implemented (`src/app/page.tsx`, `src/lib/quiz/*`, `src/components/quiz/*`). ## 2026-09-28 — Phase 6: result collection, decided against raw HTML scraping

Instructions.md says "build the game to be prepared for" URLs that vary year to year and collect laureate count/names/affiliation/citizenship/sex/age/motivation from "the official nobel prize site." Before writing an HTML scraper against `nobelprize.org`'s summary pages (which would need per-prize CSS-selector maintenance and would break silently on any template change), the site was checked for a structured alternative.

- **Decision: use the official `api.nobelprize.org/2.1` JSON API instead of HTML scraping.** `GET https://api.nobelprize.org/2.1/laureates?nobelPrizeYear={year}&nobelPrizeCategory={code}` (codes: `phy`, `che`, `med`, `eco`, `lit`, `pea`) returns, per laureate, in one call: `gender`, `birth.date`/`birth.place.country`/`birth.place.continent`, `nobelPrizes[0].motivation`, `.dateAwarded`, `.affiliations[].name`/`.country`/`.continent`, and (economics) `.topMotivation`. Organisation laureates (e.g. Nihon Hidankyo, Peace 2024) carry `orgName` instead of `knownName`/`gender`/`birth`, which is exactly the signal needed for Peace's individual/organisation/mixed question. Verified live against 2025 and 2024 data (`/tmp` scratch calls, not committed) before committing to this design. This is a public, documented API that nobelprize.org itself publishes for exactly this kind of programmatic use — no ToS concern for a small private non-commercial quiz.
- **Citizenship is not in the API, at all, for any prize** — confirming nobeldata.md's own caveat ("nobelprize.org doesn't publish citizenship for science laureates") extends to Peace and Literature too; the API only has birth country and affiliation country, neither of which is citizenship (e.g. Machado is Venezuelan by birth *and* citizenship, but plenty of laureates hold citizenship distinct from both). **Decision: the three citizenship-based questions (Literature US-citizen, Peace US-citizen, whole-week American-citizen-count) are never auto-graded** — the scraper still fetches and stores birth/affiliation country as a hint on the proposed `Result`, but grading always requires admin judgement, same as instructions.md's own Literature-genre caveat (`nobeldata.md`: "these genre labels are my own judgement"). Literature's prose/poetry/other question is likewise never auto-graded, for the same reason.
- **Africa-residence (whole-week) is auto-proposed but explicitly low-confidence.** nobeldata.md's own Peace answer key relies on each laureate's actual residence at the time of the award (e.g. Gbowee: Liberian, residing in Ghana), which the API can only approximate via affiliation-country continent (works for science/econ) or birth-country continent (fallback for Peace, which is often wrong — see the Gbowee case). The proposal is generated anyway and flagged `confidence: "low"` in `rawScrapedData` so the admin page surfaces it differently, but admin approval is required regardless (per 6.5) so an imperfect guess never reaches players unreviewed.
- **Schema addition:** `Question.gradingKey` (nullable string) and `AnswerOption.matchValue` (nullable string) were added rather than trying to regex-parse each option's free-text label (e.g. "2 laureates", "No — something else") back into a machine-comparable value. `gradingKey` names which computed signal a question is graded on (`LAUREATE_COUNT`, `PHRASE_DISCOVERY_OF`, `AFFILIATION_MIT`, `PEACE_TYPE_SPLIT`, `WHOLE_WEEK_FEMALE_COUNT`, etc.); `matchValue` is each option's canonical value for that signal (`"2"`, `"yes"`, `"individual"`, ...). Questions with no reliable auto-signal (genre, both citizenship questions) simply have `gradingKey = null` and are skipped by the grader, going straight to admin-only grading. This keeps the grader a small lookup table instead of fragile string matching against player-facing copy, and keeps player-facing option text free to be edited without touching grading logic.
- **Retry bookkeeping lives on `Result`, not a new table.** Added `Result.scrapeAttempts` (default 0) and `Result.lastAttemptAt` (nullable). The scheduler upserts a `Result` row (status `PENDING`) on first attempt for a question whose deadline has passed, and increments these on every subsequent attempt; there's no separate `FAILED` status — after the bounded attempt/time window, the row simply stays `PENDING` with `scrapeAttempts` at the cap, which the admin page treats as "needs attention" alongside genuine fetch failures. Simpler than adding another enum value for what's the same admin action either way (manual entry).
- **Found while building 6.1's verify script: `npm run build` had been silently failing since Phase 4.** `tsconfig.json`'s default `include` sweeps up everything under `**/*.ts`, including `scripts/*.ts` — which use explicit `.ts`-suffixed imports (needed for `tsx` to run them directly) that `next build`'s own `tsc` pass rejects (`TS5097`). This affected `verify-phase4.ts` and `verify-phase5.ts` too, not just the new Phase 6 script — nobody had re-run `npm run build` since Phase 0, only the per-phase Playwright/vitest verify scripts, so it went unnoticed. **Fixed:** added `"scripts"` to `tsconfig.json`'s `exclude` — they're standalone ops tooling run via `tsx`, not part of the deployed app, and were never meant to share the app's bundler-resolution import convention. `npm run build` now succeeds end-to-end again; worth remembering for Phase 9's deploy pipeline, which depends on this.
- **Admin gating:** reuses the existing `User.isAdmin` flag (already in the Phase 1 schema, unused until now). There's no admin signup flow — promoting a user is a one-off `UPDATE "User" SET "isAdmin" = true WHERE email = '...'` run by hand against the real DB when needed, consistent with "regular" auth scope (answer #8) not needing a second privileged-signup path for a single-admin, small-private-game deployment.

**Also closed a known gap while here:** Phase 0's notes flagged that `postinstall` wasn't wired to run `prisma generate`, requiring a manual step after every fresh clone/`npm install`. This session hit that exact failure mode directly — after `prisma migrate dev` added the new `gradingKey`/`matchValue`/scrape-bookkeeping fields, the generated client silently stayed stale (a confusing `Unknown argument prizeId` error, not an obvious "field not found" message) until `npx prisma generate` was run by hand. Added `"postinstall": "prisma generate"` to `package.json` so this can't recur.

**Verification summary:** `npm test` (39 tests, including new `grader.test.ts` and `scheduler.test.ts`) and `npm run build` both pass. `scripts/verify-phase6-scraper.ts` hit the live `api.nobelprize.org` API for real 2025 data — 19/19 checks. `scripts/verify-phase6-admin.ts` drove a real browser through the full reject-correct-approve admin flow and confirmed the player-facing page reflects the correction, not the original wrong proposal — 8/8 checks. ## 2026-09-29 — Display names, renaming, and chronological question layout

- **Default names are former laureates (deceased only).** New accounts get a random unused name from `src/lib/auth/laureateNames.ts` (68 entries across all six prizes). Deceased-only so no living person's name is handed to strangers as a handle; every entry is checked against `api.nobelprize.org` by `scripts/verify-laureate-names.ts`. When all 68 are taken, generation falls back to the original floral adjective+noun scheme (kept, also used by accounts created before this change — "Golden Zinnia" stays until its owner renames).
- **No schema change.** The blurb is looked up from the name at render time (`laureateInfoFor`), not stored, so a renamed user simply loses it. Custom names may not equal a laureate name (case-insensitive) — otherwise anyone could type "Albert Einstein" and inherit the "Physics 1921" blurb; laureate names are only obtainable via the random button, which excludes names already in use.
- **Renaming** lives on `/account` (linked from the main page header as "Change name"): 3–24 characters, letters/numbers/space/dot/apostrophe/hyphen (any script, no emoji or markup), whitespace collapsed, unique case-insensitively (the DB constraint is case-sensitive, so this is checked in code, with P2002 as the race backstop), rate-limited to 10 per minute per IP. No profanity filter — a small private game; the admin can rename via SQL if ever needed.
- **Question layout:** the three status sections (open / awaiting / results) were replaced by one chronological list — a block per announcement day headed "Monday 5 October · Physiology or Medicine", thin rule between days, a 4px rule and a "Whole-week questions" heading before the four whole-week questions. Each card already shows its own status (form with countdown / "Voting closed" / result). Days are Stockholm calendar days, consistent with the rest of the game. The end-of-week "Your answers this year" list uses the same layout.
